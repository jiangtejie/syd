# 数字员工的意图识别：算法与落地

> 状态：**已落地（2026-09-12）**。起因：Base 里「数字员工回复」表的**意图列大量为空**。

## 1. 问题定位（先查清楚再改）

看代码就清楚了：只有**命中话术**那条路径写了 intent，走 LLM 兜底的分支 `insertReply` 压根没传 intent：

```ts
// 修改前（services/agent/duty.ts）
intent: d.action === 'llm' ? '' : d.script.intent   // LLM 兜底 → 空字符串
```

线上库实测：58 条决策记录里 **58 条的意图全为空**，其中 46 条连规则都认不出（当时还没有识别层）。
所以这不是「列没同步」，是**根本没算过**。

## 2. 算法：三层，能停就停

| 层 | 触发条件 | 成本 | 结论来源 |
| --- | --- | --- | --- |
| **L1 话术** | 命中了话术库 | 0 | 话术自带的 intent（同事自己维护，权威），置信度 1 |
| **L2 规则** | 未命中话术 | 0（纯函数，离线可测） | 内置词典打分，置信度 ≥ 0.7 直接采纳 |
| **L3 模型** | 规则置信度 < 0.7 且本轮 LLM 还有额度 | 一次调用 | 模型**只能从标签表里选**（闭集），结果按文本 hash 缓存 |
| — | 全都没结论 | 0 | 「其他」+ 来源 `none`（**永不返回空串**） |

### 2.1 规则层打分

- 权重：强特征 +3 / 弱特征 +1 / 否定特征 −4（足以抵消一次强命中）；
- 正则只做「组合型强特征」（如 `(多久|几天|啥时候|什么时候).{0,4}(到|发)`）；
- 置信度 = clamp(0.3 + 0.12×得分 + 0.08×与第二名的分差, 0.3, 0.95)：
  得分高、且没人跟它抢，才给高置信；两个意图打架时自动降到 0.5 左右，交给模型复核。

### 2.2 为什么必须先清洗文本（这步最关键）

真实群聊里的「一条消息」常常是若干条拼起来的：

```
[图片]
@萍姐物配客服-黄巧-17723603132 老师这个鸡爪胀气了
收到
"亦春" 撤回了一条消息
```

不清洗的话，「胀气了」这个真信号会被 @提及、占位符、撤回提示淹没 —— 实测第一版 46 条里绝大部分
都因此落进「其他」。所以归一化按顺序做：

1. 全角→半角、去零宽字符、转小写；
2. **逐行剔除系统行**（撤回/入群/退群/群公告/拍一拍/聊天记录）；
3. 去会话 id 前缀（`123@chatroom:` / `...@openim:`）；
4. 去 @提及（`@名字-手机号`）但保留后面的正文；
5. 去占位标记（`[图片]/[语音]/[文件]/[消息]/[抱拳]`），文件名等正文保留；
6. 去手机号；
7. 清洗后不足 2 字 → 判为「无意图」（不是硬判成某个标签）。

### 2.3 标签表（16 个内置 + 话术库自定义）

到货时间、缺货先发、发票进度、对账单/单据、物流查询、排车安排、催单、营业时间、价格优惠、
系统下单问题、配件补发、退款退货、质量投诉、**下单订货**、**发货配送**、合同资质。

后两个是**上线后按真实数据补的** —— 线上「未归类」样本里最高频的就是「门店订货啦」「需要配送货物」。
话术库里同事自己起的 intent 会自动加入标签表（模型只能从这个并集里选，不会自创标签）。

### 2.4 模型复核的约束（防胡说）

- 只输出标签表内的词，不在表里一律按「其他」；
- 必须给 confidence，低于 0.6 视为没把握 → **保持规则层结论**；
- 返回不是合法 JSON / 超时 / 报错 → 静默回退，绝不让识别流程中断；
- 结果按文本 hash 缓存（上限 400 条，FIFO 淘汰），同一句话不重复问模型。

## 3. 可解释性：每条判定都带证据

`agent_reply` 新增三列（老库由 `COLUMN_MIGRATIONS` 幂等补上）：

| 列 | 含义 |
| --- | --- |
| `intent_source` | script / rule / llm / none（界面与 Base 显示为 话术/规则/模型/未归类） |
| `intent_confidence` | 0~1，低于阈值时界面提示「待确认」 |
| `intent_evidence` | 命中的词（顿号分隔），同事质疑时能当场复现，而不是「模型说的」 |

## 4. 历史数据补全（一次性 + 可重跑）

- 入口：值班页「补全历史意图（N 条）」按钮（只跑规则层，零成本，**不动决策与发送状态**）；
- 逻辑：`backfillReplyIntents()` —— 待识别 = 意图为空 **或** 上次判成「未归类」（词表升级后可重跑）；
- 重跑时不把已有结论降级成「其他」（避免 其他↔其他 来回刷）；

## 5. 线上实测（真实数据）

| 阶段 | 结果 |
| --- | --- |
| 补全前 | 58 条决策记录意图全空 |
| 第一版词表（无清洗） | 补上 58 条，但 **46 条落进「其他」** —— 说明词表与清洗都不够 |
| 加清洗 + 2 个新标签 + 扩充词表 | 重跑后：「下单订货 6、发货配送 5、对账单 3、价格优惠 2、质量投诉 1…」，未归类降到 **32** |
| 剩余 32 条「未归类」 | 逐条看过：**撤回提示、纯应答（好/收到）、`[消息]`、@客服+无正文** —— 本来就不是业务问题，判「其他」是对的 |
| 推到 Base | 「意图」列 58/58 非空；新增「意图来源」列（未归类 32 · 规则 26）；再跑同步 **created 0 / updated 0 / skipped 58**（幂等） |

## 6. 顺带修掉的两个同步缺陷（都是这次实测踩出来的）

1. **少一列会让整条记录被拒收**：新加的「意图来源」列在同步时还不存在 → 58 条更新全部失败。
   修法：`syncRepliesOut` 同步前先 `ensureFields()` 补齐列（幂等，多一次 listFields）。
2. **刚建的列写入会被忽略 + hash 记住了**：补列当轮写入被飞书丢掉，之后 hash 一致 → 永远跳过，
   新列一直是空的。修法：补列后 `invalidateSyncHashes('reply')` 主动作废 hash，下一轮重写一遍把新列填上。
3. **「记录没了」的判定过宽**：原来 `/1254/` 会把**字段类**错误（同为 1254xxx）当成记录不存在 →
   丢映射 → 下一轮重复插入（实测 58 条变 116 条，已清理）。现在只认 `RecordIdNotFound|record not found|记录不存在`。
