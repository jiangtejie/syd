# 议题证据明细同步到多维表格:设计与落地记录

> 状态:**已落地(2026-09-12)**,P0 + P1 全部实现并通过 typecheck / lint / build,映射层有离线自检覆盖。
> 唯一未实测的环节是「关联字段」的字段类型码(见 §7),代码里已做失败退化,不会阻塞同步。
> 前置:议题同步(含写进指定表 / 一键配置)已落地并提交(`86c8280`)。

## 0. 结论(推荐并已采用)

**单开一张「议题证据」子表(一行一条消息),不要把证据塞进议题那一行的单元格**;
议题表可选加一个「关联证据」字段(单向关联),让同事点开议题就能看到证据。

四条理由:
1. Base 单元格文本有长度上限,几十条消息塞一格既看不全也难读;
2. 证据是 **append-only**(消息不可变)→ 天然幂等,子表按 证据ID 映射一次即可,不需冲突处理;
3. 子表可**筛选/排序/分组**(按议题ID、按时间、按来源),一眼看清"这个议题客户到底说了什么";
4. 隐私可控:证据子表可以单独设权限/单独建视图,不必把原文和议题行绑死。

## 2. 三个方案对比

| 方案 | 做法 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- | --- |
| A 单元格内嵌 | 议题行加「证据明细」多行文本列,把 N 条消息拼成一坨 | 零新增表 | 有长度上限、不可筛选、几十条没法读、一眼看不出时间线 | ✗ 不推荐(仅适合极少证据) |
| **B 子表(已采用)** | 新表「议题证据」,一行一条消息 + 议题ID/序号/时间/发送人/内容/类型 | 可分组筛选排序、幂等简单、量放大也不挤、隐私可控 | 多一张表 | ✓ **已实现** |
| C 每议题一篇飞书文档 | 证据导出为文档,议题行放链接 | 长文 + 图片体验最好 | 每议题一次建文档、权限与清理复杂、量大时噪音大 | 后续可选(适合"复杂客诉复盘") |

## 3. 推荐方案(B)详设

### 3.1 子表「议题证据」字段(已实现)

| 字段 | 类型 | 来源 | 说明 |
| --- | --- | --- | --- |
| 证据ID | 文本 | msg.id | **幂等键**(写入映射用) |
| 议题ID | 文本 | issue.id | 与议题表同名列;不依赖关联字段也能按它分组/筛选 |
| 议题标题 | 文本 | issue.title | 冗余一份,肉眼可读(否则只看到一堆 ID) |
| 客户群 | 文本 | issue.groupName | 便于跨表对照 |
| 序号 | 数字 | 1..N | 该议题内证据顺序(按 seq) |
| 时间 | 日期 | msg_time | 时间线排序 |
| 发送人 | 文本 | sender_name | 昵称,便于读懂谁说的 |
| 来源 | 单选 | is_send / is_team | 客户 / 我方同事 / 我方 |
| 内容 | 文本 | text | 截断(见 3.4)。非文本写 `[图片]`/`[语音]`/`[视频]`/`[表情]`/`[链接/卡片]`/`[名片]`/`[位置]` 占位 |
| 类型 | 单选 | local_type / image_md5 | 文本 / 图片 / 语音 / 视频 / 表情 / 链接-卡片 / 名片 / 位置 |
| 证据图 | 附件 | (P2) | 本地解密后上传,一期先不做 |

> 注意:证据表**只用标准列名**,不套议题表的「列名映射」——这张表是我们自己建的,列名可控;
> 套映射反而会让同事改一个设置就把证据塞错列。

### 3.2 幂等与增量(已实现)

- 映射:kind='evidence', local_id=msg.id → record_id;新增走 `batchCreate`,映射表保证不重复插;
- 增量来源:repo `listEvidenceForSync({sinceMs, limit})`(JOIN issue_feedback 保证议题还在、带 序号/标题/群名);
- 首轮量控制:默认只推**最近 7 天**、每议题最多 **20 条**("首现 1 条 + 最新 19 条"),避免几千行一次灌表;
- 限流:100 条/批 + 120ms 间隔,失败只计入 failed 不中断;
- 删除:议题删除会级联删证据 → 远程行成孤儿。P1 提供「清理孤儿行」按钮:按**本地真实证据 id 集合**比对远程「证据ID」(不能用映射表判断,映射行在议题删除后仍会残留),只删我们自己写入的行,不动同事手填的行。

### 3.3 关联字段(已实现,带退化)

- 议题表加「关联议题」(单向关联 → 议题证据表);建表后尝试创建,失败只记 warn;
- 用的是 REST 数字类型码 `type: 18` + `property.table_id`(对应"单向关联"),与 CLI 指南的 `type=link` + `link_table` 同义;
- **未实测**:本机无法在不落数据的前提下跑一次 dry-run,所以代码把失败当正常分支处理——
  失败时设置页会显示「未建立关联字段(不影响同步):可在证据表按「议题ID」分组查看」;
- 退化路径:用「议题ID」文本列 + Base 视图按 议题ID 分组,功能等价,只多一次点击。

### 3.4 隐私与截断(默认保守,已实现)

- 证据 = 客户原文 → **默认不推**(开关 `推送证据明细（客户原话）` 默认关);
- 打开后仍受三重上限:每条截断(默认 200 字)、每议题条数(默认 20)、范围(默认近 7 天),三个值都在设置页可改(20~2000 字 / 1~200 条 / 1~365 天);
- 非文本证据写占位标记(P2 再做真图附件);
- 设置页写明"客户原话会写入飞书表格,注意敏感信息",并在开关上方显示当前生效的三个上限与"本轮待推 N 条"。

### 3.5 限流与性能(已实现)

- 复用现有 100 条/批 + 120ms 间隔 + 串行;
- 首次全量只推近 7 天,后续按增量推(映射表命中即跳过);
- 同步历史单独记 kind='evidence',设置页历史里显示为「证据明细」,监控页同步 toast 也会报"证据新增 N"。

| 位置 | 增加 |

| 设置页 → 同步历史 | kind 显示中文(议题 / 影子回复 / 证据明细 / 拉取同事改动) |

> **P2c 为什么不做(用户判断 + 复核结论一致)**:一篇议题的「复盘」信息已经在三个地方各就各位 ——
> ① 议题表行本身(状态/跟进人/处理备注三列,同事在手机上直接改);② 「议题证据」子表(逐条证据 + 证据图附件,
> 首现→最新完整时间线);③ 聚合层面的飞书日报(digest,一次一篇覆盖当天的量级与趋势)。
> 再给每个议题生成一篇 docx,等于把同一批数据搬进**第二个真源**:议题状态变了文档不会自动更新、
> 每篇文档各有一份协作者与生命周期要管、量大时还会在飞书里堆出上百篇低信息量文档。
> 真要「给同事/上级看一篇完整复盘」,更合适的是**按需、单议题**导出(选中议题 → 一键导出为飞书文档,走审批桥),
> 而不是默认每议题一篇;那条等有真实诉求再做。

## 9. 证据附件(图片)的落地细节

### 9.1 为什么只做图片

证据行来自 `issue_feedback_msg`,它的列只有 `text / image_md5 / local_type` —— **视频与文件消息没有
md5 落库**,拿不到本地文件,所以这两类仍只写占位标记(要做就得先给证据表加 video_md5/file_md5 列
并在写证据时带上,属于数据模型改动,单独排期)。语音同理(要先把 SILK 解成 wav 再上传)。

### 9.2 表格侧

- 「议题证据」表新增 **证据图**(附件,type=17);
- 老表(功能更早版本建的)没有这一列:**开了附件开关时每轮先跑一次 `ensureEvidenceTable`**,
  `ensureFields` 只增不改,自动补齐;
- 附件字段值写成 `[{file_token}]`(飞书要求),通过 `batchUpdate` 写回对应记录。

### 9.3 上传链路(三步)

1. **本地解密**:复用监控页看图那条链路 `mediaService.decryptImage({wxid, imageMd5, kind:'orig'})`,
   产物落在 `<cache>/media/<账号>/<md5>_orig.<ext>`,再用 `resolveMediaUrl()` 反解绝对路径
   (这个函数从 `mediaArchive` 导出复用,不另写第二份);
2. **上传素材**:`drive/v1/medias/upload_all`,`parent_type=bitable_image`、`parent_node=Base app_token`;
3. **写附件列**:拿到 `file_token` 后 `batchUpdate` 写入证据行的「证据图」。

### 9.4 幂等与限额

| 机制 | 做法 |
| --- | --- |
| 同一张图只传一次 | `lark_media_map(md5 → file_token)` 缓存;命中直接复用,不走网络 |
| 同一条证据只写一次附件 | `lark_evidence_attach(msg_id)` 标记;**只有 batchUpdate 成功才标记**,失败下一轮重试 |
| 单张上限 | 默认 10MB(飞书 upload_all 单次上限 20MB),超限跳过并保留 `[图片]` 占位 |
| 每轮上限 | 默认 20 张,避免一轮打几百个 multipart;剩下的下一轮继续 |
| 补齐历史 | 开关常常是后开的:每轮会把「已推送、图片、但没写附件」的历史证据行补上(同样受每轮上限约束) |
| 换 Base / 清配置 | 清空两张缓存表:file_token 是 Base 级的,换表即失效 |

### 9.5 踩坑(已在代码注释里钉住)

**SDK 的 `drive.v1.media.uploadAll` 不返回统一的 `{code,msg,data}` 包装**,而是直接把
`{file_token, version}` 放在顶层。第一版复用了 `larkCall()`(它按 `res.data` 取值),
结果「上传成功但没有返回 file_token」——素材其实传上去了,token 被丢掉了。
现在单独包了 `larkUploadMedia()` 处理这种返回形状,并把这段写进注释防止后人再踩。

### 9.6 实测(真实凭证,2026-09-12)

| 项 | 结果 |
| --- | --- |
| 补列 | ✅ `ensureEvidenceTable` 在既有证据表上补出「证据图」(type=17),`fieldsAdded: ['证据图']` |
| 解密 | ✅ 本地真实证据图解密成功(165,135 字节) |
| 上传素材 | ✅ 拿到 `file_token`(并写入 `lark_media_map`,后续复用) |
| 写附件 | ✅ 建了一条测试记录带上「证据图」→ 成功,随后**已删除**该记录 |
| 副作用 | 上传素材共留下 2~3 个未被引用的素材(验证过程产生,单个约 160KB),不影响表格数据 |

### 9.7 隐私

图片是**比文字更敏感**的内容(可能是身份证、合同、聊天截图),所以:
- 附件有**独立开关**,默认关闭,与「推送证据明细」分开;
- 只有证据明细开关打开、附件开关也打开时才会解密上传;
- 设置页在该开关旁写明「会先解密到本地缓存再上传」,并给出单张/每轮上限。

**为什么文件证据不做上传**:微信文件附件是 `.dat`(需要按账号密钥走 `datDecrypt` 那条链路,还要从 XML 里解析原始文件名/大小),
做半成品比不做更糟(会出现「有时传上去有时不传」的静默失败)。当前只把 md5 与文件名登记进证据表,
等真有「客户发的报价单/合同要进 Base」的诉求再补。
