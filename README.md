# 微信私域智能客服工作台 · wechat-cs-desktop

本机运行的微信客服工作台：直接读取你本机的微信数据，把「客户消息 → 问题提取 → 跟进 → 收尾」做成可追踪的闭环，并把 AI 用在回复建议、群问题提炼、复盘与营销内容上。

- **本地优先**：没有自建后端、没有遥测；聊天内容只在本机处理。只有你主动开启的能力才会把内容送出去 —— AI 提交流向你配置的大模型通道，数据上报流向你自己配置的 PostgreSQL。
- **对外发送有闸门**：默认需要人工确认（可配审批策略），并带日限额、熔断与发送审计；发送结果会回查微信库做「闭环校验」。
- **AI 通道可换**：任意 OpenAI 兼容接口 —— OpenAI / DeepSeek / 阿里百炼 / 智谱 / Moonshot / 硅基流动 / 火山方舟 / Ollama / 自定义。
- **Windows 桌面应用**（Electron），亦提供 macOS / Linux 构建脚本，但主力与验证平台是 Windows。

> ⚠️ 请仅用于你自己拥有合法访问权限的微信账号与数据，并遵守微信服务条款与当地法律法规。本项目不提供任何绕过平台限制的能力。

## 功能全景

界面分七个页面（左导航）+ 设置：

| 页面 | 能力 |
| --- | --- |
| **对话** | 会话列表（群/单聊/公众号，群徽标显示待处理问题数）、消息面板（文本/图片/视频/语音/表情/文件/引用/转账，图片视频本地解密缓存，语音点开即解码播放）、右侧「回复建议 / 本群问题」双视图、消息右键「标记为团队客服」、在聊天中定位问题、渠道接收文件托盘、工作区（会话绑定本地目录，AI 可读写） |
| **监控** | 问题监控中心（管理者视角）：KPI 大卡、新增/解决趋势、类型分布、群 Top、积压年龄、钻取列表（状态处置/指派跟进人/严重度筛选/分页）、追踪抽屉（证据时间线 + 定位聊天 + 处置动作）、维护操作（全量重析/取消/合并重复/归档历史/清空）、快照导出 |
| **看板** | 私域运营指标：消息量/收发比/群私聊分布/24h 分布、**跟进队列**（有未读且最后一条是客户的会话，越久越靠前）、沉睡召回、发送质量（闭环校验通过率、失败原因 Top） |
| **AI** | AI 工作台（对话式）：绑定工作的智能体、技能包、工具调用卡片、工作区读写；内置快捷问题（今日待跟进清单、群复盘等） |
| **客户** | 客户档案：按会话聚合标签（群/个人/公众号、活跃度、待办）、备注与历史问题 |
| **营销** | 营销增长模块：内容采集（抖音/小红书）、素材仓库、爆款分析、舆情监控（门店相关评论/提及）、AI 二创与合规检查、发布导出 |
| **数据** | 会话导出（TXT / HTML / JSON，含附件引用）、业务报表、媒体归档 |
| **设置** | 微信数据与密钥、AI 通道与智能体、发送策略、飞书（通知/机器人/云文档）、定时任务与数据上报、问题监控口径、日志、缓存与数据管理 |

后端（主进程）能力：

- **微信数据接入**：定位并解密本机微信库（支持多分片消息库；页级 AES-256-CBC + HMAC 预校验、流式解密、WAL 只在「当前日志」时才合并、明文副本按容量限额自动收敛），会话与消息读取（keyset 分页 / 增量 sortSeq 读取）、联系人/群昵称 enrich、企微与会话类型识别、库变更监听（WAL 变化事件）。
- **群问题闭环引擎**（见下节）。
- **回复建议**：本地背景下拉（本群待办、历史问题、团队名单）+ 只读工具循环 + 多候选输出；支持智能体人设与话术库。
- **发送执行**：审批闸门、排队（上限 20）、日限额、失败熔断（**状态持久化，重启仍拦截**）、审计落库、发送后闭环校验；发送前做**目标唯一性预检**（同名/前缀撞车/包含关系一律拒绝，避免发错群），只在「粘正文之前」的失败才安全重试一次。
- **数据上报**：定时任务把会话/消息/媒体增量同步到你自己的 PostgreSQL（游标增量、媒体归档、进度与取消、运行历史）。
- **飞书集成**：长连接机器人（收消息/图片/文件并任务化、按身份分级响应、指令闭环）、告警推送（新问题/盯办）、云文档能力（Docx / Wiki / Sheets / Base / 妙记 / 画板等，经 lark-cli 工具注册表暴露给 AI）。
- **媒体解码**：微信图片（.dat）解密（内置密钥自动推导，失败可手填）、视频缓存、**语音 SILK → WAV 就地播放**、表情包解析、附件归档。
- **统一日志**：分级分模块写 `userData/logs/app-YYYY-MM-DD.log`，设置页可近实时查看。

## 群问题闭环（核心引擎）

目标：群里的客户诉求**一条都不丢、不重复、有归属、能收尾**。

### 1. 提取

- 窗口：增量按**水位**（时间 + sortSeq 双线，补录/回拨的旧时间消息也能读到）；首次/重算按自然日窗口（默认 2 天，面板可选 1/2/3/7 天），向前扩展以覆盖 open 议题的锚点（上限 14 天）。
- 方式：OpenAI 兼容 LLM 按「会话段」分批提炼议题（每批 ≤200 行，超长群自动分批消费，避免截断丢段）；未配置或调用失败时**回退本地规则**（关键词聚类 + 末尾未回复兜底），面板会标注本次是「AI 提炼」还是「规则」。
- 落库：稳定 key upsert（人工状态、指派、疑似确认不会被重析覆盖）；新增问题数按**真正新建行**计数。
- 防漏：读取窗口按 800 条上限截断时，群问题面板会显示「覆盖 N 条 · 条数超限未覆盖全窗口」。

### 2. 跟进判定 —— 规则管跟进、LLM 管闭环

每轮分析（以及后台**每 2 分钟**的收尾巡检：零 LLM，只读消息 + 判定）对全部 open 问题做**确定性判定**，不再依赖「LLM 下次是否又提到它」：

- **归属式判定**：每条我方/团队消息归属给「最近一条客户消息的发送人」，只看**本议题客户名下、且不早于议题锚点**的回复 → **跟进中**，并记录回复时刻与回复人；客户连发多条（补图、追问、@客服）之后再回复也能正确识别；
- 无归属回复 → **待处理**（客户在等回复）；锚点本身就是我方/团队消息（模型把客服回复当最早证据）→ 视为已在处理中；
- 判定依赖「我方同事」名单：同事需在对话页右键「**标记为团队客服**」，或在监控页/群问题面板的证据时间线里点「**标记同事**」；群问题面板顶部还有「**同事标记**」折叠区，按发言人聚合一次勾选标完（避免一个个点）——未标记的同事发言会被当成客户发言，议题会一直停在待处理；
- **静默收尾**：客服已回复、该客户此后静默超过 `monitor.autoCloseHours`（默认 72h，可配，0=关闭）→ 自动「已解决（自动）」，可重新打开复核；
- **超期搁置**：锚点超出 14 天回溯范围仍无法判定 → 自动「已搁置」；
- 跟进超时按「客服最后回复时间」动态计算（`monitor.followUpHours`，默认 12h）。

### 3. 防重复

同一议题只保留一条，三层保险：

1. 提取时 LLM 可指认「与既有待办 #N 是同一条」，直接复用其 key；
2. 附录行优先保住每个 open 议题的**锚点行**，让模型看得见原议题，从源头减少 key 漂移；
3. 同一性判据兜底（`src/main/services/feedback/issueSimilarity.ts`，阈值用真实数据标定）：
   - 标题相似度（真重复 ≥0.40，不同主题 ≤0.20）；
   - 证据消息重叠率（引用同一批消息，不受时间跨度限制）；
   - 同客户 + 同类型 + 时间邻近（仅作无证据交集时的弱兜底）。

判据分**强/弱**两档：高置信（证据几乎完全重合 / 标题逐字一致 / 同客户同类型且证据被包含）由后台**自动合并**；弱信号（仅时间邻近）只在监控页「合并重复」里**预览确认**后才合并。合并保留最早一条（合并证据、取最高严重度、并集客户、沿用指派跟进人），其余归档为 `duplicate` —— 不计入闭环率与趋势、也不算「不是问题」的反例样本，需要时可重新打开。

### 4. 归属与盯办

- **跟进人**：团队成员（对话页右键「标记为团队客服」）可指派；未指派但有人回复过时，聊天右侧面板直接给「+ 指派给 XXX」一键指派。
- **盯办升级**：未指派超时（紧急 >1h / 其余 >4h）、已指派但长期无人回复（默认 8h）、跟进超时 → 应用内提醒 + 飞书推送；同一问题的重复提醒间隔**递增**（45min → 90min → 3h → 6h），不再轰炸。
- **复发识别**：同群同客户同类型、上次已闭环后再次出现 → 标「复发×N」并回溯上次处理。

### 5. 口径与统计

- 闭环率 = 已闭环（含已闭环后归档）÷（已闭环 + 待处理 + 已搁置 + 已闭环后归档）；
- 「今日解决/趋势」用**闭环时间**（resolved_at），不会被重析刷新污染；
- 监控总览由**主进程按全量数据**聚合（KPI/趋势/分布），明细限量回传（默认 1000 条，超限提示）；
- 「归档历史」把 90 天前已闭环记录归档，活跃列表/盯办/徽标只留近期，闭环率与趋势照旧统计。

## 数字员工（值班自动应答 · 一期影子模式）

部署在一台闲置电脑上，代替「人盯群」：**按话术自动应答客户群**。一期只**记录不发送** —— 先让它把「这条该不该回、按哪条话术回」算出来给你看，话术和风险分校准到位后再开正式模式。

**判定顺序**（`services/agent/matcher.ts`，纯函数可自检）：

1. **不介入**：我方/同事已发言、纯应答（收到/好的）、事务性通知（发货明细/对账单）、图片语音等非文本、内容过短；
2. **命中话术**：按优先级取第一条命中（关键词 / 正则），回复模板支持 `{{客户名}} {{群名}} {{日期}} {{时间}}`；
3. **未命中** → LLM 兜底生成草稿（受每轮条数上限约束）；
4. **风险分级**：`A` 可自动发；`B` 需人工确认；`C` **永不自动**（价格/退款/投诉/合同/质量）→ 直接转人工。

**设计原则：只承诺动作，不承诺事实。** 客户问「孜然粉到货了没」，一期答「我查一下到货进度，确认后马上回复您」，绝不说「明天到」——到货时间/库存数字依赖实时业务数据，等二期接入订单与物流查询工具后才直接作答。

**怎么用**：

1. **话术库**（左侧「值班」页 → 话术库）：点「导入推荐话术模板」得到 15 条落地话术（问到货/缺货先发/发票/对账单/物流/排车/催单/系统下单异常/配件补发 + 3 条 C 类禁自动），按自己的口径改；
2. **群开关**（左侧「客户」页）：顶部「数字员工」条可**批量**开启/关闭/跟随默认，列表每行也有单独的开关（带 `*` 表示该群未单独设置、跟随全局默认）；采购/内部群先在「监控」里排除，自动回复会一并跳过；
3. **看它会怎么回**（值班页 → 影子记录）：逐条反馈「👍 答得对 / 👎 答错了 / 🚫 不该回」，反馈是后续调话术的依据；
4. **回放预演**（值班页 → 回放预演）：拿最近 1–7 天的真实消息跑一遍，不写库不发送，直接看覆盖率与误回。

> **上线前的前置条件**：「我方同事」名单必须标全。没标记的同事发言会被当成客户，数字员工会去回自己同事的话（真实数据里就有一位物配文员 39 条发言未被标记）。群问题面板的「同事标记」折叠区可一次补齐。

**一期不做**：不发送、不理解图片语音（这类消息一律转人工）、不管单聊。

## 协作面：议题同步到飞书多维表格

单机看板只能自己看，同事在门店/仓库根本没有客户端。所以把**议题**推到飞书多维表格（Base），
同事在手机上就能看与处理 —— 这是「多人协作」的最低成本方案（零 Web、零账号体系）。

**怎么用**：设置 → AI 助手 → 飞书云文档 → 「议题同步到多维表格」 → 粘贴 Base 链接 →
「验证并建表」（自动创建「议题」「数字员工回复」两张表与字段，并写一条测试记录验证写权限）→
打开「定时同步」或点「立即同步」/「拉取同事改动」。

**同步范围（只这几列是双向的）**：

| 方向 | 列 | 说明 |
| --- | --- | --- |
| 本地 → Base | 议题ID / 客户群 / 类型 / 严重度 / 标题 / 摘要 / 状态 / 跟进人 / 首现时间 / 最近更新 / 证据条数 | 默认**脱敏**：只推标题与摘要，不推聊天原文（可在设置里打开） |
| Base → 本地 | **状态**、**跟进人**、**处理备注** | 同事在表格里改这三列才会被采纳回本地；处理备注在客户端里**只读展示**（群问题面板与监控抽屉都能看到同事的结论） |
| 本地 → Base | 数字员工**影子记录**（判定/意图/拟回复/风险/人工反馈） | 推送到「数字员工回复」表，手机上就能审话术；触发消息默认截断 120 字（打开「推送聊天原文」放宽到 500） |

**冲突规则**：本地权威。若本地行的 `updated_at` 晚于我们上次推送时间，这一轮**不采纳**对方的值
（下一轮会把本地值写回 Base）；反之采纳。判断「是不是同事改的」靠 `lark_sync_map.remote_*`
（上次同步时 Base 上的值）与 Base 现值比对 —— 否则自己刚写上去的值会被误判成同事改的，来回打架。

**两条容易踩的坑**：

1. **Base 没有唯一键**：写之前无法靠字段去重，只能靠本地 `lark_sync_map(kind, local_id → record_id)`
   记映射，再用内容 hash 跳过无变化的写；
2. **权限是两步**：开放平台开通 `bitable:app`（读写）并发布版本 + 把应用加为该 Base 的**可编辑协作者**。
   只开只读会「读得到写不进」，「验证并建表」会明确报出来。

**节奏**：定时同步每 2 分钟一轮，**先拉后推**（先把同事改的应用回本地，再推本地变更 —— 反了会覆盖对方）。

### 每日日报

配置在 **设置 → 飞书通知 → 每日日报**：**独立开关**（有人只想要日报、不要实时告警）+ 推送时间（默认 09:00）+ 是否附数字员工统计。

推送内容（手机上 ≤ 20 行）：

```
📋 群问题日报 · 09-12
新增 3 · 已解决 5 · 待处理 12 · 其中无人应 4 · 跟进中 6 · 跟进超时 2

⏰ 积压最久
1. [保利星荟店对接群] 物流·孜然粉到货（等了 2天3小时） · 跟进:陈西西

🙋 无人应（客户在等）
1. [南部店物配对接群] 售后·鸡爪到不了（等了 1天5小时）

👤 在手量：陈西西 4 · 黄巧 2
🤖 数字员工（影子）：命中话术 12 · 转人工 3 · 未命中 5 · 话术覆盖 60%
```

三个刻意的设计：**① 与告警分开开关**（共用接收目标与日限额）；**② 按天幂等**（重启或多轮 tick 都不会重复发）；**③ 没有待办也照发一句**「今天没有待处理问题 ✓」—— 定时任务静默死掉是最难发现的事故。设置页有「立即发一条看看」可先预览文案。

```
│     ├─ ai/                    模型通道、建议 Agent、工具注册表、工作台引擎、能力分层/技能包
│     ├─ send/                  发送执行与闸门
│     ├─ report/                定时任务·数据上报（→ PostgreSQL）
│     ├─ lark/                  飞书（长连接/消息/联系人与云文档工具）
│     ├─ im/                    外部 IM 渠道（飞书/微信 ClawBot 等）
│     ├─ growth/                营销增长（采集/仓库/舆情/二创/发布/导出）
│     ├─ export/  media/        导出、媒体与文件
│     └─ logging.ts  paths.ts  统一日志、路径与缓存分区
├─ preload/                     contextBridge 桥（接口真源在 src/shared/api.ts，实现与声明双向校验）
├─ renderer/                    React 界面（pages / components / stores / lib）
└─ shared/                      两端共享：types、growth、monitorMetrics、api(桥接口)
```

**进程与数据流**：渲染端只通过 `window.api.cs.*` 调 IPC；主进程独占本地库与微信库访问；微信库变更由 WAL 监听触发事件广播（`cs:wx:dbChanged` / `cs:issue:changed` / `cs:issue:progress` 等），页面据此增量刷新。

详见 [ARCHITECTURE.md](ARCHITECTURE.md)（微信接入 / 密钥 / 消息读取 / AI 建议 / 发送执行 / 本地数据模型 / 配置键）。

## 快速开始

### 环境要求

- **Node.js** `^20.19.0 || >=22.12.0`（electron-vite 5 要求）
- Windows 10/11（主力平台）、macOS、Linux 亦可构建
- 本机安装并登录过微信（需要能读到微信数据目录）

### 安装与开发

```bash
npm install          # 依赖（含 Electron 二进制）

npm run dev          # 开发模式（主进程/预加载/渲染端热更新）
npm start            # 预览构建产物
```

> 改到 **preload 或主进程**时，热更新只换界面、不换桥 —— 界面会出现「⚠ 维护功能未加载」或按钮点了没反应，**完全退出应用重启**即可。

### 构建与打包

```bash
npm run build             # 类型检查 + 三端构建（产物在 out/）
npm run build:win         # 打包 Windows 安装包（需要能访问 GitHub 下载 Electron/NSIS）
npm run build:win:offline # 内网/无外网时用本地 Electron 打包（等价于 --config electron-builder.offline.yml）
npm run build:mac         # 打包 macOS
npm run build:linux       # 打包 Linux
```

产物：`dist\wechat-cs-desktop-1.0.0-setup.exe`（约 120 MB，NSIS **按用户安装**，装到 `%LOCALAPPDATA%\Programs`，不需要管理员）。
安装包**未做代码签名**，Windows SmartScreen 会提示「未知发布者」→ 点「更多信息 → 仍要运行」。

**目标机器（客户/门店电脑）需要什么**：Windows 10/11 x64 + **微信桌面版并登录要托管的那个账号**；不需要 Node、不需要本仓库。
首次启动会自建 `%APPDATA%\wechat-cs-desktop\cs.db`（含建表与迁移），日志在同一目录 `logs\`。

**打包常见坑**：

- 内网/被墙环境：`npm run build:win` 会卡在下载 Electron 或 NSIS 上（TLS 断连/超时），改用 `build:win:offline`；
- 原生模块：`better-sqlite3-multiple-ciphers` 是 N-API 预编译（`prebuilds/win32-x64.node`），打包时由 electron-builder 自动解包到 `app.asar.unpacked`，跨 Node/Electron ABI 都可用；
- 冒烟自检：`dist\win-unpacked\wechat-cs-desktop.exe --user-data-dir=<空目录>` 可以模拟「干净机器首次启动」（不影响正式数据）。

## 首次配置

1. **微信数据与密钥**（设置 → 微信数据与密钥）：填写微信数据根目录，导入 64 位十六进制密钥；图片密钥可点「自动推导图片密钥」从本机 `*_t.dat` 模板反解（失败仍可手填）；库密钥点「自动获取密钥」会依次尝试三个来源 —— 可选组件（自备已授权组件）、外部工具（自备取 key 命令，输出里含 64 位十六进制即可，`.cmd` 也支持）、本地文件（在指定路径里找别的工具导出过的 key）；**任何候选都要通过真实库的页 1 校验才会导入**，失败会逐条告诉你卡在哪，最稳妥仍是手动导入。密钥用 Electron `safeStorage`（操作系统级加密）保存，主进程持有明文，渲染端只看到状态。连接成功后即可在「对话」页看到会话。
2. **AI 通道**（设置 → AI）：选预设或自定义 Base URL + API Key + 模型名，可建多个智能体（人设/风格/自定义提示词）。未配置也能用：群问题提取自动退化为规则模式，回复建议退化为话术库匹配。
3. **发送策略**（设置 → 发送）：是否允许 AI 参与发送、是否需审批、日限额。
4. **飞书**（可选，设置 → 飞书）：填应用凭证后开启长连接机器人（收消息/图片/文件）、问题告警推送、云文档读取。
5. **数据上报**（可选，设置 → 定时任务）：填自己的 PostgreSQL 连接串，创建 `chat_sync` 任务增量同步会话/消息/媒体。

## 数据、密钥与隐私

| 内容 | 位置 |
| --- | --- |
| 应用本地库（问题/会话索引/配置/审计） | `%APPDATA%\wechat-cs-desktop\cs.db`（SQLite，WAL）。审计表（IM 审计 / 飞书发送 / 发送日志）按 `db.retentionDays` 保留，默认 90 天 |
| 日志 | `%APPDATA%\wechat-cs-desktop\logs\app-YYYY-MM-DD.log`（默认保留 7 天，可配） |
| 缓存分区 | 非系统盘优先：`<盘>:\wechat-cs-desktop\cache\{db,media,files,tmp,export,growth}`，可在设置里改 |
| 解密后的微信明文库副本 | `<cache>\db`（源库路径 + 密钥相同则复用同名文件；按 `plainCacheMaxMB/Files` 自动收敛，可随时清理） |
| 媒体解密产物 | `<cache>\media\<wxid>\`（图片/视频）与 `\voices\`（语音 WAV），经 `ct-media://` 协议只读暴露；按 `wechat.mediaCacheKeepDays`（默认 180 天）/ `MaxMB`（默认 8GB）自动回收 |
| 上报媒体归档 | `<cache>\media\<wxid>\archive\`（数据上报的 `media_path` 指向这里；**不参与**缓存淘汰，只显示占用） |
| 微信密钥 | `cs.db` 中 `safeStorage` 密文；不落明文、不出本机 |

对外数据流只有两条，且都由你显式配置：**AI 通道**（聊天片段用于提炼/建议）与**数据上报**（你自己的 PostgreSQL）。除此之外应用不发起任何外部请求，也没有账号体系与遥测。

## 排障 FAQ

**「合并重复」等维护按钮点了没反应？**
先看监控页工具栏是否出现「⚠ 维护功能未加载」：出现说明 preload 还是旧的（热更新不换桥），**完全退出应用重启**。仍无反应就看「设置 → 日志」（模块 `issue`）：有 `重复议题预览 …` 说明点击已到主进程；没有则是渲染端未加载到新桥。

**任务状态一直停在「待处理」，同事明明回复过？**
三条排查：(1) 该同事是否已标记为团队客服（群问题面板的「同事标记」折叠区可批量勾选，或时间线里点「标记同事」、对话页右键标记）；(2) 回复是否发生在议题锚点之后；(3) 判定是异步的——最多等 2 分钟（收尾巡检周期），或在群问题面板点一次「重新分析」立即刷新。

**群问题面板一直显示「规则」而不是「AI 提炼」？**
AI 通道未配置或调用失败。到设置里检查 Base URL / Key / 模型名，然后点面板「重新分析」。

**面板提示「条数超限未覆盖全窗口」？**
该群消息量超过单次扫描上限（800 条），只分析了最新部分。缩小窗口天数重析，或分批处理。

**监控页提示「明细已加载 N/M 条」？**
KPI/趋势按全量统计，明细为控制传输量只回传最近 1000 条。用状态/类型筛选，或点「归档历史」把 90 天前的已闭环记录收起来。

**监控页报错 / 列表空白？**
典型原因是「渲染端比主进程新」：热更新或重新加载窗口只换了界面与预加载桥，**主进程仍是旧版**，新的 IPC（如 `cs:issue:overview`）没有对应 handler，调用即失败。页面会自动退回兼容通道并显示「⚠ 主进程版本较旧」，**完全退出应用重启**即可恢复。任何新增 IPC 的功能在重启前都可能不可用。

**为什么改了代码界面变了、功能没变？**
同样是 preload/主进程未重启（见上）。判断方法：界面出现「⚠ 维护功能未加载」或「⚠ 主进程版本较旧」。

## 开发约定

- **提交风格**：中文 `type: 摘要(要点)`，`type` 取 `feat/fix/perf/refactor/style/docs/chore/build`；正文写清「为什么」与关键口径。
- **改动前**：跑一遍 `npm run typecheck`；改到判据/去重逻辑时先跑 `npm run test:similarity`（它是唯一有断言的回归网）。
- **分层约束**：渲染端不得直连本地库；跨端接口一律登记到 `src/shared/api.ts`（`CsApi`），preload 实现对着它编译，漏改即编译失败。
- **数值调参**：判据阈值、窗口、上限都写成模块级常量并注明标定依据，别散落在调用点。
- **注释口径**：注释写「为什么这么定」，不写「这行在做什么」。

## 已知限制与路线图

**已知限制**

- 语音**能解码播放**（SILK → WAV），也能**本地转写**（自备 whisper.cpp 可执行文件 + 模型，全程离线）：气泡上点「转写」，`npm run test:asr` 可验证重采样与参数拼装；转写按需触发、不做历史批量回填，未转写的语音在分析与数字员工里仍是 `[语音] N″` 占位。
- 无 AI 通道时退化为规则提取，召回率明显下降（面板会标注「规则」）。
- 单群单次扫描 800 条、全量重析活跃群前 30，超出都有显式提示。
- 边界议题仍需人工复核：疑似桶（规则弱命中）与去重预览是刻意保留的人工关口。
- 没有单元测试框架；目前靠 `tsc` + ESLint + 构建 + 判据自检脚本兜底。

**路线图（未做）**

- 语言模型输出「闭环依据」并落库，让自动闭环可审计。
- 问题明细服务端分页（当前为限量回传 + 归档收敛）。
- 更细粒度的团队 SLA（按人/按类型设定跟进时限）。
